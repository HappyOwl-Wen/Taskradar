# TaskRadar 修改后 UI / 交互复查

日期：2026-10-16。版本基准：`3eb46a2`，对照[上一轮报告](UI_UX_REVIEW.zh-CN.md)及 `3776e94..HEAD` 的前端改动。

本次只审查 UI 与用户交互，没有审查后端业务逻辑。使用最新源码生成的正式构建，在独立临时数据目录中运行，关闭后台定时任务；只操作本次创建的合成任务、演示邮箱和两个合成 `.eml` 文件。没有修改用户原有任务、邮箱授权或凭据。测试环境显示的“后台任务没有运行”由本次启动方式造成，不列为产品缺陷。

检查覆盖 390×844、1024×768、1440×900 视口，中文浅色主要流程及英文深色抽查。前端 `npm run build` 通过，`npm test` 的 19 个测试文件、104 项测试通过。没有运行后端测试。真机软键盘、完整屏幕阅读器流程以及所有网络异常场景不在本次覆盖范围内。

## 1. 结论

上一轮的核心改进已经落实：新建只需一句话，编辑后确认具有明确主动作，设置离开保护覆盖主导航和浏览器返回，审核页面不再强行在 1024 px 下挤成双栏，手机导入按钮也有了名称。导航、元信息和低频工具已经明显收敛。

现在最应该修的是新增完成控件的状态反馈，以及手机连续审核时的通知遮挡。数量口径、恢复后的淡出状态和下一项的阅读位置也会让用户怀疑操作是否生效。这些问题无需再增加功能，主要需要让同一项任务在不同位置的表现保持一致。

| 编号 | 优先级 | 问题 | 验证方式 |
| --- | --- | --- | --- |
| R-01 | P1 | 全部视图中完成、恢复后的勾选框与实际展示状态相反 | 实际操作、可访问性树、DOM、截图 |
| R-02 | P1 | 手机成功通知遮住下一项的确认与编辑按钮 | 连续审核、DOM 矩形、截图 |
| R-03 | P2 | 恢复任务后仍保留半透明淡出样式 | 实际操作、computed style |
| R-04 | P2 | 导入摘要把任务与建议相加，显示 3 件，队列只有 2 件 | 同批合成文件导入、首页与队列对照 |
| R-05 | P2 | 自动进入下一项时保留旧滚动位置，返回与进度被滚出视野 | 手机连续审核、scrollTop 与焦点检查 |
| R-06 | P2 | 日期修正弹窗遗漏造成冲突的星期信息 | 日期冲突用例、弹窗内容检查 |
| R-07 | P2 | 关联任务改名后，建议卡片仍显示旧名，对比弹窗显示新名 | 实际编辑、建议与对比内容对照 |

以下结论均针对界面显示和操作体验，不据此推断数据存储、日期识别或合并算法的正确性。

## 2. 当前需要修复的问题

### R-01 / P1：完成控件在数据更新后显示反了

**复现步骤**：

1. 在“我的任务 → 全部”打开一个未完成任务。
2. 点击左侧圆形控件完成任务。
3. 移开鼠标，观察勾选框。
4. 再点击它恢复为未完成，观察结果。

**实际结果**：完成后标题有删除线、状态菜单显示“已完成”，但圆圈仍为空心，`aria-checked` 为 `false`；恢复后标题和菜单已经回到未完成状态，`aria-checked` 却为 `true`。鼠标悬停时的绿色图标会暂时掩盖第一个问题。

**原因在前端显示状态**：`shownDone` 在 mutation 成功后仍根据 `next` 推导；收到更新后的任务属性后，`done` 和 `next` 已经反转，但 `isSuccess` 仍保持为真，于是再次反转了显示结果。全部视图和保留同一条目的搜索结果会受到影响；未完成视图里条目直接离开列表时不容易看见。

**建议**：只在请求进行中使用明确记录的目标状态；成功后显示当前任务状态，或在新任务属性到达后清理临时状态。勾选框视觉、可访问性属性、标题样式和菜单状态应使用同一结果。

**验收**：同一个组件实例在完成、恢复、撤销和数据刷新之后，勾选状态始终正确；不依赖刷新整个页面才能恢复。

代码：[状态推导](../frontend/src/components/tasks/StatusMenu.tsx#L110)、[可访问性与图标](../frontend/src/components/tasks/StatusMenu.tsx#L122)。现有 [CompleteToggle 测试](../frontend/src/components/tasks/StatusMenu.test.tsx#L32)主要检查首次点击，没有覆盖操作成功后用更新的任务属性重新渲染同一实例。

### R-02 / P1：手机成功通知挡住下一项的关键动作

**复现步骤**：在 390×844 视口中确认一项任务，或执行“编辑后确认”，让队列自动进入下一项。

**实际结果**：底部成功通知及其“撤销”按钮覆盖下一项的吸底操作栏。“确认任务”“编辑后确认”“忽略”位于通知后面，用户需要先关闭通知或等待，无法顺畅连续审核。

DOM 矩形检查中，确认按钮约在 y=788–832 px，通知在同一区域跨越约 y=755–846 px；截图确认两者实际相交。通知位置会随入场动画略有移动，覆盖关系已经可以直接观察到。带撤销的成功通知配置为显示 10 秒。

**影响**：最常用的下一步操作被上一次操作的反馈遮挡，还可能把本想确认下一项的触摸落到撤销区域。

**建议**：手机通知为底部动作栏预留空间，或把“刚才已确认 / 撤销”放进队列内的固定反馈区域。保留撤销机会，保证提示出现时也不遮挡操作。无需仅靠缩短提示时间来规避。

**验收**：通知显示期间仍能直接操作下一项；短通知和长任务标题通知都应检查。

代码：[全局通知位置](../frontend/src/App.tsx#L110)、[通知时长](../frontend/src/lib/queries.ts#L144)、[审核动作栏](../frontend/src/components/tasks/TaskDetailView.tsx#L554)。

### R-03 / P2：恢复任务后仍像被禁用

**复现步骤**：在全部视图中完成任务，再恢复为未完成，切换到“未完成”视图。

**实际结果**：条目仍带有 `opacity-40`，实测 `opacity: 0.4`。它可以点击，但外观像已经失效或正在消失；离开页面再回来才恢复。

**原因**：任务 ID 放入 `leaving` 集合后，只在请求出错时移除；成功和恢复时没有清理。全部视图的动作也会写入集合，切换到未完成视图后才显现淡出样式。

**建议**：将淡出状态限定为当前离场动画的生命周期。成功离开列表、重新出现在列表或完成撤销/恢复时都需要清理；不离开当前视图的操作不应留下长期淡出标记。

**验收**：完成再恢复、完成再撤销，以及全部/未完成视图切换后，仍存在的任务均恢复正常透明度。

代码：[leaving 集合](../frontend/src/pages/TasksPage.tsx#L106)、[写入与清理入口](../frontend/src/pages/TasksPage.tsx#L168)、[样式应用](../frontend/src/pages/TasksPage.tsx#L359)、[透明度](../frontend/src/components/tasks/TaskRow.tsx#L150)。

### R-04 / P2：导入结果的“件数”又出现重复计算

**用例**：导入两封合成邮件，两者都是同一事项的通知，日期不同；本次显示产生两个新任务和一条疑似重复建议。

**实际结果**：尚未处理这批任务时，首页“最近一次导入”写“发现 3 件需要你确认的事”，紧接着却是“2 件事等待你决定”；侧栏与统一队列也都是 2。

**前端原因**：导入反馈直接使用 `created + suggestions`，把新任务和该任务附带的建议相加，然后把这个和称作需要确认的“事”。持续结果卡和 toast 都采用这个口径。

**建议**：若没有可用于去重的任务集合，直接写“发现 2 个新任务，另有 1 条需核对建议”，不要把两种单位相加为任务数。进入队列的入口仍保持一个。

**验收**：包含新任务、重复建议、日期变更的同一批导入中，各位置的数字含义清晰且一致。历史导入结果可以保留当时的统计，但应使用明确的单位。

代码：[持续结果卡](../frontend/src/components/sources/LastImport.tsx#L77)、[导入通知](../frontend/src/lib/upload.ts#L102)。

### R-05 / P2：自动下一项没有重置阅读位置和焦点

**复现**：在手机上向下阅读较长任务并确认，队列自动进入另一项。

**实际结果**：新任务的详情滚动区仍有 `scrollTop: 90`；“返回列表”和进度已经滚出可视区域。焦点回到 `BODY`，没有进入新任务标题或新的主要动作。

**影响**：用户需要先判断自己在哪里，再向上滚动找任务位置；使用键盘连续操作时也失去当前工作位置。

**建议**：切换 activeId 后重置详情窗格的滚动，并将焦点移动到新标题或其他明确的起点；列表自己的滚动位置可以保留。明确区分“保留列表位置”和“从新任务开头开始阅读”。

**验收**：从任意滚动位置确认/跳过后，新项的标题、日期和位置提示可见；键盘焦点有明确去向。

代码：[下一项与焦点](../frontend/src/pages/InboxPage.tsx#L76)、[持续存在的详情滚动区](../frontend/src/pages/InboxPage.tsx#L233)、[仅重新挂载内部详情](../frontend/src/pages/InboxPage.tsx#L266)。

### R-06 / P2：日期修正弹窗缺少完整的冲突依据

新版日期说明已经能准确指出“日期与星期对不上”，这是已改善之处。测试原文为 `Freitag, 4.11.2026`，界面按日期显示为周三。

**剩余问题**：点击“修改日期”后，弹窗里的原文只剩 `4.11.2026`，遗漏了 `Freitag`。用户在决定按日期还是按星期时，恰好看不到造成冲突的那部分内容，需要关闭弹窗返回查看。

**建议**：带入包含星期、日期和相对时间锚点的完整句子，必要时突出冲突片段。日期输入的自动聚焦可以继续保留。

**验收**：用户在修正弹窗内就能理解为什么需要改日期，不必关闭弹窗来回对照。

代码：[传入的上下文仅为 due_text](../frontend/src/components/tasks/TaskDetailView.tsx#L254)、[编辑表单中的上下文](../frontend/src/components/tasks/TaskEditDialog.tsx#L396)。

### R-07 / P2：建议中的关联标题与对比弹窗不一致

**复现**：对疑似重复的一对任务，把已有任务的标题改为“交互复查：提交 Musterkurs TR-204 材料”，再查看另一任务的重复建议。

**实际结果**：建议卡仍引用原来的德文长标题；打开“查看差异”，已有任务一栏和合并说明都显示新标题。相同的对象在不同层级使用不同名称。

**影响**：用户可能以为建议涉及另一项任务，不得不打开对比才能确认身份。

**建议**：统一关联任务展示数据，优先使用当前标题；生成建议时的旧标题仅用于历史记录或当前信息缺失时的明确回退。首页已经采用优先读取当前字段的方向，详情和建议卡需要保持一致。

代码：[详情中的旧快照优先](../frontend/src/components/tasks/TaskDetailView.tsx#L218)、[建议卡](../frontend/src/components/tasks/SuggestionCard.tsx#L63)、[共用 payload 读取](../frontend/src/lib/review.ts#L190)、[首页当前字段优先](../frontend/src/pages/DashboardPage.tsx#L85)。

## 4. 仍可继续减少的界面负担

下面是设计改进建议，优先级低于上述具体操作问题。

- **添加内容页仍有三处“导入文件”**：全局顶栏、页头主按钮、手动导入来源行。保留页头作为该页主入口，顶栏按页面隐藏或弱化，来源行主要展示已有文件和管理入口即可。对应位置：[页头](../frontend/src/pages/SourcesPage.tsx#L56)、[来源行](../frontend/src/components/sources/SourceCards.tsx#L448)。
- **首页的“没有需要关注”与冲突列表矛盾**：本次没有近期截止事项，但有两项日期冲突，页头仍说“目前没有需要你关注的事项”，下面却显示需要决定和需要关注。可以改成“近期没有到期任务，另有 2 件事需要确认”；不应让一个只统计近期截止的句子概括所有问题。对应位置：[摘要判断](../frontend/src/pages/DashboardPage.tsx#L306)、[文案](../frontend/src/i18n/zh-CN.ts#L344)。
- **重复事项继续集中展示**：同一对日期冲突任务在“等待决定”和“需要关注”各出现一遍。首页保留一个主入口，另一处用摘要指向它，能继续降低“是不是又多了一件事”的误解。
- **手机对比弹窗仍然很长**：本次 390 px 下可视高度约 811 px，内容高度约 1546 px，虽然没有横向溢出，但决定按钮位于很后面。可以先给日期/标题差异摘要，再展开完整行动和来源，操作区保持可达。
- **普通用户不必反复看到实现术语**：例如新建时的“不会自动补成 23:59”可改成“时间可留空，只按日期提醒”；调试详情继续放在次级菜单。新功能默认不新增一排常驻控件，先判断是否属于当前任务的下一步。

## 5. 建议下一批工作

先修 R-01、R-02，并把 R-03 一起处理，让“完成—恢复—继续审核”的反馈稳定。随后统一导入计数与关联任务标题，补齐切换任务后的滚动/焦点处理和日期依据。最后再做入口去重与对比弹窗缩短，不需要继续扩大功能面。

现有 104 项测试通过仍会漏掉这些问题，建议补充真正跨状态的检查：

1. 同一完成控件收到更新后的任务属性，勾选仍正确。
2. 在未完成列表完成后撤销/恢复，条目透明度回到正常。
3. 手机通知显示期间，底部审核动作仍可见且能点击。
4. 两个新任务附带一条重复建议，摘要不把它称为三个不同任务。
5. 滚动后的任务确认完成，下一项从合适的阅读起点开始。
6. 关联任务改名后，建议摘要和对比使用同一名称。
