# TaskRadar 界面与用户交互审查

审查日期：2026-10-16。目标：让第一次使用的人迅速理解操作逻辑，让经常使用的人用更少的判断和点击完成任务。

本次检查了本地运行界面、前端组件、中文文案、样式，以及仓库中的深色与英文示例截图。实际浏览覆盖仪表盘、待确认、重复对比、任务列表、来源、设置、运行洞察，以及新建和编辑弹窗；重点验证了 1440×900、1024×768、390×844 三种视口。没有审查后端业务逻辑，也没有确认、完成、忽略、删除现有任务或变更已保存设置。设置草稿检查只编辑未保存的测试值，离开后已确认原值仍为 Europe/Berlin。

这是专家审查，不是真实用户实验；下文的学习成本判断是设计判断，时间与成功率指标是建议的后续验收目标。深色和英文主要依据现有截图及样式检查，未冒充完整的运行时回归测试。手机视口检查不等同于真机软键盘测试。

## 1. 总体判断

目前值得保留的基础包括：统一的蓝灰配色和线性图标、任务与原文证据关联、列表与详情并排审核、审核动作吸底、日期冲突需要明确选择、撤销操作，以及已经默认折叠的历史和技术详情。这些能帮助用户建立信任，不需要整体推翻。

最主要的负担来自信息组织和动作表达。界面经常要求用户先理解“候选任务、待处理建议、需核实、已确认、进行中、运行洞察”等分类，再决定操作位置；同一件事还会重复出现在多处。新建任务也一次暴露了太多字段。对易用性而言，应优先缩短任务路径，再调整视觉细节。

| 优先级 | 本报告中的含义 | 应先处理的事项 |
| --- | --- | --- |
| P1 | 会造成错误预期、丢失输入或妨碍关键操作 | 编辑后确认的实际默认行为、设置草稿离开保护、窄屏溢出、新建表单过重 |
| P2 | 会增加理解、寻找和重复操作成本 | 导航概念、完成入口、仪表盘层级、重复入口、图标与控件可见性、导入反馈 |
| P3 | 基础路径稳定后补充的体验完善 | 动画、减少动态效果、长列表、持续的新用户引导 |

## 2. 已复现的具体缺陷

### UX-01 / P1：“编辑后确认”默认只保存

**复现**：进入待确认任务，点击“编辑后确认”。弹窗底部的“保存并确认”复选框默认未选中，主按钮显示“保存”。

**影响**：用户按照入口文案操作，会预期编辑并保存后任务已经被确认、开始提醒；实际还需要发现并勾选另一个控件。这种偏差发生在核心流程中，比单纯的按钮样式问题更应优先处理。

**建议**：从这个入口进入时，主动作默认且明确地显示“保存并确认”。若需要保留仅编辑能力，可以提供次要动作“只保存修改”；普通“编辑任务”入口仍可默认只保存。两个入口的意图应直接传递给表单。

**验收**：用户无需额外勾选即可完成“编辑后确认”；保存前可以从按钮文字判断结果。

**代码位置**：[入口](../frontend/src/components/tasks/TaskDetailView.tsx#L128)、[默认值](../frontend/src/components/tasks/TaskEditDialog.tsx#L156)、[复选框与按钮](../frontend/src/components/tasks/TaskEditDialog.tsx#L268)。本次只验证了 UI 默认状态，没有提交任务变更。

### UX-02 / P1：通过主导航离开设置时，草稿静默丢失

**复现**：在常规设置的时区中输入未保存的测试值。切换到其他设置分类，会弹出“有未保存的更改”；选择继续编辑后，点击左侧“全部任务”，页面直接离开，没有同类提示。返回设置，草稿已消失。

**影响**：相同的“离开页面”动作具有不同保护规则。用户可能在完成一段较长配置后失去输入，也会误以为此前的设置已经保存。

**建议**：把未保存保护覆盖到站内路由离开、浏览器前后退和关闭窗口。或者保存本地草稿，并明确展示“未保存”，在返回时恢复。单独绑定设置分类按钮不足以覆盖用户真实的导航方式。

**验收**：通过分类、侧栏、搜索跳转和浏览器导航离开时，保护行为一致；不丢失未提交输入。

**代码位置**：[仅处理分类切换的 select](../frontend/src/pages/SettingsPage.tsx#L112)、[窗口关闭保护](../frontend/src/pages/SettingsPage.tsx#L107)。

### UX-03 / P1：390 px 手机和 1024 px 双栏审核页出现横向溢出

**复现**：选择现有的测试任务“Einverständniserklärung Musterkurs TR-204”，查看“需要你核实”区域。长文本和操作组合使内容超出详情窗格，“查看差异”“修改日期”位于可视区域右侧，原文也需要横向滚动才能完整阅读。

实测 DOM 尺寸：390 px 视口下详情滚动区可用宽度约 375 px，内容滚动宽度为 453 px；1024 px 视口下对应宽度约为 445 px 和 541 px。两种情况下都不是单纯的文字省略，而是整个详情内容发生溢出。

**影响**：用户可能看见问题说明，却找不到解决问题的按钮。1024 px 又同时保留完整侧栏和任务列表，进一步压缩了实际操作区域。

**建议**：对详情网格及各 section 明确允许收缩，检查子网格的最小内容宽度；长文本允许断行，提示动作在窄容器内独占一行。双栏断点应根据详情剩余宽度决定，1024 px 时可折叠侧栏或采用列表/详情切换。不能只隐藏横向滚动条。

**验收**：中文、德文长单词、长来源标题和多个问题同时存在时，正文及关键动作均无需横向滚动；390 px 与 1024 px 都应纳入检查。

**代码位置**：[Section](../frontend/src/components/tasks/TaskDetailView.tsx#L52)、[提示行](../frontend/src/components/tasks/TaskDetailView.tsx#L243)、[双栏与列表宽度](../frontend/src/pages/InboxPage.tsx#L101)、[侧栏宽度](../frontend/src/components/layout/Sidebar.tsx#L87)。

### UX-04 / P1：快速新建仍然是一张完整配置表

**复现**：点击“新建待办”。快速输入下面仍然同时展示标题、需要做什么、说明、类别、优先级、日期、时间、时间含义。390×844 视口下，未输入任何内容时，“保存”按钮的顶部已经在约 y=986 px，首屏内不可见。

**影响**：一行自然语言输入的便利，被下面整张表抵消。“标题”“需要做什么”“说明”还会让新用户停下来判断三者差别。“时间含义”是模型术语，普通用户更容易理解“截止前完成”或“在这个时间参加”。

**建议**：默认只展示一句话输入、识别出的可编辑日期和“添加待办”。类别、优先级、说明等收进“更多选项”。没有明确区别的标题和行动描述不应都要求用户在默认视图中考虑。手机表单采用底部操作区，让保存动作保持可达。

**验收**：仅填写标题即可完成创建；普通新建无需展开高级选项；手机用户能在输入后直接找到添加按钮。

**代码位置**：[完整表单](../frontend/src/components/tasks/TaskEditDialog.tsx#L215)、[页尾按钮](../frontend/src/components/tasks/TaskEditDialog.tsx#L274)、[弹窗整体滚动](../frontend/src/components/ui/dialog.tsx#L14)。

### UX-05 / P2：手机导入按钮缺少可访问名称

**复现**：视口小于 sm 时，导入按钮只剩图标；可访问性树中对应节点显示为空名称的 button。相比之下，“新建待办”在隐藏可见文字后仍有 aria-label。

**影响**：屏幕阅读器用户无法判断该按钮的用途；普通新用户也只能猜测向上的箭头代表上传、导入还是同步。

**建议**：补齐独立的可访问名称。手机上优先为“添加”保留文字，把低频主题和语言入口收进更多菜单，腾出空间给主要动作。可见文案和可访问名称应随“正在导入”状态一起更新。

**代码位置**：[UploadButton](../frontend/src/components/layout/TopBar.tsx#L47)。

### UX-06 / P2：状态未知时曾短暂显示为“未连接”

**观察**：来源页首次进入时曾显示 Gmail“未连接 / 前往连接”，而设置页已显示已连接；随后状态加载完成，来源页恢复为正常。该现象是暂态显示，不能据此断言邮箱授权或后端连接存在问题。

**前端证据**：来源卡片把尚未取得的 status 通过 Boolean 转成 false，再展示未连接。

**建议**：区分“加载中”“暂时无法确认”“未连接”和“需要重新授权”，加载失败时保留上次已知状态并给出重试。不能让数据尚未返回的过程引导用户重复连接邮箱。

**代码位置**：[GmailRow](../frontend/src/components/sources/SourceCards.tsx#L113)。

### UX-07 / P2：首页重复建议有时只显示另一任务为“—”

**观察**：首页的多条“疑似同一件事”建议显示“任务 A 与 —”；进入详情和对比后，另一任务的标题可以正常看到。用户在首页不能凭摘要判断建议是否值得马上处理。

**前端证据**：首页摘要直接读取 related_task_title；详情使用的 suggestionPayload 已包含从 payload.other_title 回退读取的能力。

**建议**：所有摘要复用统一的展示模型；若确实没有标题，显示“查看另一项任务”或明确的加载/不可用状态。不要把裸破折号当成有意义的对比对象。

**代码位置**：[首页摘要](../frontend/src/pages/DashboardPage.tsx#L126)、[已有的回退处理](../frontend/src/lib/review.ts#L153)。

## 4. 颜色、排版、图标、图案与动画

### 颜色：保留配色，调整视觉权重和控件边界

蓝色主动作、紫色待确认、橙色需核对、红色逾期/失败、绿色完成已经有一致基础。无需为了“更丰富”增加更多颜色。应减少同一行同时出现多种彩色标签，把最紧急且可操作的一项放在前面。

当前通知角标无论通知级别都使用红色，会让一般未读也获得逾期级别的视觉强调。可以保留未读数量，但将普通信息使用中性色，红色留给真正需要注意的异常。

有一个需要实修的颜色细节：浅色模式未选中复选框的边框实测为 `oklch(0.869 0.022 252.9)`，背景为白色。按 sRGB 相对亮度计算，边框与背景对比度约 **1.48:1**，边界较难辨认。优先加深交互控件边框，装饰性卡片边框仍可保持轻淡。用于识别控件的必要视觉信息通常应满足 3:1 的非文本对比要求；这不同于要求所有分割线都达到 3:1。[W3C 非文本对比说明](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

正文及辅助说明应分别核对实际背景上的文字对比度，普通文字以 4.5:1 为基线。本次没有对整个应用做穷尽的合规认证。[W3C 文字对比说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

代码：[颜色变量](../frontend/src/index.css#L37)、[复选框](../frontend/src/components/ui/form.tsx#L27)、[通知角标](../frontend/src/components/layout/Notifications.tsx#L45)。

### 排版：让任务正文获得空间

现有 22 px 页标题、16 px 区块标题、14 px 正文可以沿用。需要调整的是默认密度：任务行中的来源、类别、建议数量、状态和双行日期同时竞争空间；德文长标题尤其容易被截断。

建议默认只展示两层信息：第一层为任务标题和日期，第二层为最重要的异常或一句必要说明。普通元信息进入详情。手机标题允许两行，日期可以移到下一行，避免固定日期列挤压标题。关键提醒和动作避免依赖 11–12 px 的小字；来源时间等非关键元信息才适合较小字号。

任务详情继续以“做什么—什么时候—为什么”为顺序。原文证据和来源列表可以保留，但让“查看完整原文”承担第二层展开，减少相近内容在首屏重复。技术详情已折叠，应保持这一点；常规用户的主路径也不需要反复显示“调试用”入口。

### 图标和点击尺寸：信息图标与操作按钮要有区别

保留现有 Lucide 线性图标体系，不需要混入另一套图标或 emoji。优先修复语义：空心圆究竟是完成框、当前状态还是菜单，不应依赖用户试点才能知道。

实测复选框仅 16×16 px；常用审核动作约 32 px 高，部分次要按钮 28 px 高，弹窗关闭按钮 24×24 px。可以保留 16 px 图形，但扩大实际点击区域；手机高频动作建议采用约 44×44 px 或更大的操作目标。

WCAG 2.2 AA 的目标尺寸基线是 24×24 CSS px，另有间距等例外；44×44 px 是更高等级的增强标准和适合本项目的触控目标，不能把所有 32 px 按钮都直接判为不合格。[W3C 最小目标尺寸](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)、[增强目标尺寸](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)

### 图案和插画：用于解释首次使用

不必在任务列表增加装饰插图、背景纹理或大幅雷达动画。它们会占用阅读空间。

适合增加图形的地方是空状态：用三个小步骤表示“添加邮件/文件 → 核对提取结果 → 获得提醒”，配一个推荐动作。现有空工作区虽然有引导，但同时给出导入、演示邮箱、Gmail、监控文件夹四张等权选项。应先推荐一个最容易完成的入口，其他放进“其他添加方式”；手动新建也应纳入清晰的第一次体验。

该引导目前在已有 recent_jobs 时便不再出现。建议引导依据用户是否完成第一次成功确认来收起，或允许从帮助里重新打开，避免首次导入没有发现任务后失去指导。

代码：[现有四入口引导](../frontend/src/pages/DashboardPage.tsx#L199)、[显示条件](../frontend/src/pages/DashboardPage.tsx#L280)。

### 动画：帮助理解发生了什么

当前动态主要是加载闪烁、旋转图标和悬停过渡。没有证据表明需要加入更多持续性动画。

建议补充少量有意义的反馈：添加成功后短暂突出新条目，完成时让该条目轻微淡出并提供撤销；审核转到下一项时明确显示进度并保持合理焦点。过渡可从约 120–180 ms 的短时长试起，以真实操作体验调整。

长时间识别显示“正在读取文件 / 正在识别文字 / 正在整理待办”等可确认的阶段；只有取得真实进度时才展示百分比。避免只显示一个无解释的旋转图标。提供减少动态效果支持，关闭非必要的闪烁和位移动画；现有前端没有找到 `prefers-reduced-motion` 或对应 motion-reduce 分支。

## 5. 建议的简化使用结构

用户首先需要知道三件事：今天要处理什么、哪些内容需要自己确认、如何添加新内容。高级功能继续保留，但在相关情境下出现。

```mermaid
flowchart LR
    A["添加内容<br/>写一句待办 / 导入文件 / 连接邮箱"] --> B["待确认<br/>核对标题、日期、重复或更新"]
    B --> C["我的任务<br/>今天 / 即将到期 / 无日期"]
    C --> D["完成<br/>可撤销，可查历史"]
```

手动待办经过可见预览后可直接进入我的任务，不需要人为多加一次审核。自动提取的内容沿用已有的确认机制；新任务、重复、日期更新在队列里分别给出恰当动作，无需用户先选择一个技术类别。

| 界面 | 默认让用户看到 | 按需展开 |
| --- | --- | --- |
| 今天 | 今天与逾期任务、一个待确认摘要、一处添加入口 | 统计、完整关注列表、系统状态详情 |
| 待确认 | 一项任务、日期、关键原文、当前需要做的决定 | 全部来源、复杂对比、历史 |
| 我的任务 | 未完成任务、明确的完成动作、必要筛选 | 批量管理、已忽略、规则复核、测试数据 |
| 添加内容 | 文件导入或连接邮箱、最近导入结果 | 文件夹监控、其他来源、演示工具 |
| 设置 | 外观、提醒、账号连接 | 模型参数、自动化策略、诊断与运行记录 |

这一结构可以通过现有组件渐进调整。不要为了简化又新增一套长期可见的“简易/专家模式”切换；优先使用统一的默认界面和按需展开，减少用户首先需要决定的事项。

## 6. 实施顺序与验收

**第一批：修正具体错误与关键可达性。** 处理 UX-01、UX-02、UX-03、UX-05、UX-06、UX-07；加强复选框边界。优先防止错误预期、丢输入和按钮不可见。这批以局部前端修改为主。

**第二批：缩短日常路径。** 简化新建表单，让完成动作一步可达；统一“任务/待办”称呼；收敛重复搜索和新建入口；仪表盘先显示行动，统计后置；导入结果增加持久入口与“去确认”。

**第三批：调整信息架构与首次使用。** 整合待确认任务和更新建议的呈现，降低运行洞察的导航权重；改造 Gmail 分步连接和按成功体验推进的引导；统一保存规则，再补充动画与焦点反馈。

**随着数据增加再验证。** 目前任务列表请求限制 300 项，待确认请求限制 500 项；没有在对应页面看到分页或继续加载入口。当前数据规模下没有复现遗漏，属于达到上限后的界面风险。届时应明确显示“已显示 300 / 共 N 项”，并提供分页或加载更多，不能让用户以为看到全部。来源处理记录已有“显示更多”，可保持交互一致。

代码：[任务列表上限](../frontend/src/pages/TasksPage.tsx#L106)、[待确认列表](../frontend/src/pages/InboxPage.tsx#L36)。

建议找 5 位没有接触过项目的人完成以下任务。这个规模用于发现明显阻碍，不足以证明总体用户群的统计表现。

| 场景 | 建议验收目标 |
| --- | --- |
| 第一次打开 | 30 秒内能说出软件用途，并指出添加入口和待确认入口 |
| 创建“明天下午交报告” | 约 1 分钟内完成；不需要理解类别、优先级、时间含义 |
| 核对一个带日期的识别结果 | 能说明确认以后会发生什么，并找到原文依据 |
| 修改后确认 | 无需额外解释“保存”和“确认”的区别即可完成 |
| 完成一项待办 | 从列表一步完成；误操作后能找到撤销或恢复 |
| 离开未保存的设置 | 无论选择哪条导航路径都不丢输入 |
| 手机与小屏笔记本 | 核心流程无横向滚动，关键按钮可见或容易到达 |
| 识别失败或连接状态未知 | 能判断下一步，且不会误以为必须重新授权 |

记录首次点击、犹豫位置、误操作和是否需要口头提示。先看这些行为，再决定是否增加引导文案；尽量让界面本身解释操作。
